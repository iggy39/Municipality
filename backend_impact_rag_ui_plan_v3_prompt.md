# Backend Impact Prompt For Municipality RAG UI Plan v3

Use this prompt with a backend-focused AI agent.

```text
You are working in /Users/igor/Desktop/projects/Municipality.

Task: Analyze the backend impact of the new Municipality RAG UI Plan v3. Do not implement unless explicitly instructed. Produce a concise technical plan explaining what current backend fields exist, what fields are missing, which pipeline stages must change, and what API compatibility strategy should be used.

Context:
The UI plan is moving to a search-first, contract-first extended POC. It introduces future-shaped contracts for:
- SearchIntent
- TopicNode + FocusedTopicTreeContext
- Decision / MunicipalAction with time anchors
- Open controlled codelists
- EvidenceReference aligned with RAG v2 artifacts
- MapEntity with separate schematic vs real geometry
- Low-confidence resident/admin modes

Important current backend facts:
- Current `decision` schema in `migrations/003_m3_decisions_citations.sql` has `decision_text`, `decision_number`, `agenda_item`, `parser_confidence`, `metadata_json`, and `is_public`, but does not persist `decision_kind`, `outcome_status`, `legal_effect`, `primary_time`, `time_anchors`, `normalized_by`, or `curation_status`.
- Current `decision_citation` stores document/page/offset citation anchors, but not bbox, retrieval artifact id, retrieval set id, or header path directly.
- Current `semantic_node` schema in `migrations/004_m4_semantic_tree.sql` has hierarchy fields: `parent_node_id`, `depth`, `node_kind`, `semantic_type`, `pref_label_he`, confidence, status, and metadata. It does not directly expose UI fields like `sibling_ids`, `path_ids`, `generated_label`, `curated_label`, `origin`, `curation_status`, `merged_from_topic_ids`, `split_from_topic_id`, `hidden_from_public`, or topic decision/time rollups.
- Current RAG v2 storage in `migrations/012_m12_rag_v2_structure.sql` has `retrieval_artifact.artifact_id`, `artifact_kind`, `header_path_json`, page spans, offsets, source kind, citation label, and retrieval text.
- Current `decision_request_context` in `migrations/014_m14_remove_legacy_chunk_rag.sql` stores `source_artifact_ids_json`, subject topic/address/cadastre fields, and confidence.
- Current `artifact_topic_annotation` in `migrations/015_m15_artifact_topic_annotation.sql` stores artifact-level structural/primary/secondary topic labels and classifier metadata.
- Current `/search` returns `chunk_id` as the artifact-like id, plus `artifact_kind`, `header_path`, `start_page`, `end_page`, and semantic fields.
- Current `/semantic/tree` returns flat `items` with `id`, `label`, `kind`, `semantic_type`, `depth`, `parent_id`, confidence, status, and child_count.
- Current `/semantic/node/{node_id}` returns parent, children, aliases, linked decisions, linked artifacts, and mentions.
- Current `/decision/{decision_id}` returns decision text, meeting info, vote, citations, linked documents, and decision request context, but not the new codelist/time-anchor fields.
- Current `RagCitation` in `src/municipality/rag_answering.py` still uses `chunk_id` naming, but RAG v2 cutover says retrieval is artifact-native. Treat this as a naming/adapter issue to inspect carefully.

New UI contract requirements:
1. SearchIntent:
   - decision_about_topic
   - activity_near_place
   - city_activity_overview
   - source_lookup
   - unknown

2. TopicNode:
   - parent_id, child_ids, sibling_ids, path_ids, depth, sort_order
   - generated_label, curated_label, origin, curation_status
   - merged_from_topic_ids, split_from_topic_id, hidden_from_public
   - category_ids, primary_category_id
   - mention_count, decision_count, recent_activity_at
   - time_rollup
   - decision_rollups by codelists
   - evidence_refs

3. Decision / MunicipalAction:
   - primary_time
   - time_anchors
   - decision_kind
   - outcome_status
   - legal_effect
   - raw_decision_text
   - normalized_by
   - curation_status
   - topic_ids, entity_ids, timeline_event_ids, evidence_refs

4. Open codelists:
   - Controlled, versioned, extensible lists.
   - Public UI only uses approved active codes.
   - Candidate codes may be generated by models but must stay non-public until reviewed.
   - Users ask natural Hebrew; aliases map user language to codes.

5. EvidenceReference:
   - source_type, source_title, source_url
   - retrieval_artifact_id
   - artifact_kind
   - retrieval_set_id
   - header_path
   - page_span
   - offsets and optional bbox
   - confidence label and extraction warnings

6. MapEntity:
   - spatial_representation: schematic | real | mixed | none
   - schematic_shape separated from real_geometry
   - real geometry must not be invented from low-confidence evidence.

Questions to answer:
1. Which of these fields can be derived today from existing tables/API responses without migrations?
2. Which fields require new persistence?
3. Which fields should be computed API-side as view models instead of stored?
4. Which pipeline stage should populate each missing field?
5. How should open codelists be modeled so they are governed, versioned, searchable, and safe for public UI?
6. How should topic tree siblings/path/children be exposed from existing `semantic_node.parent_node_id`?
7. How should decision time anchors be extracted from meetings, decision text, citations, and document metadata?
8. How should RAG v2 evidence be exposed without keeping legacy `chunk_id` naming in public UI contracts?
9. What API endpoints should be added or changed for the Explorer UI?
10. What is the lowest-risk migration path that preserves existing `/ask`, `/search`, `/semantic/tree`, `/decision/{id}` behavior?

Expected output:
- Short summary of backend impact.
- Table: UI field -> current source -> missing? -> proposed backend change.
- Proposed migrations, if needed.
- Proposed API response adapters.
- Proposed pipeline changes.
- Risks and verification plan.
- Do not write code.
```
